## 1.2 项目解决什么问题（一切学习的锚点）

**业务问题**：企业有大量私有文档（制度/手册/FAQ），但——
1. 员工找不到（检索效率）
2. 直接问大模型会瞎编（幻觉）
3. 文档更新后答案过期（时效）

**解决方案**：把文档变成"可问答、可溯源、有质量保障的知识服务"。三个关键词对应三大设计：
- **可问答** → RAG 检索引擎（第三章）
- **可溯源** → 引用标注 + 四阶段可视化（3.5 / 5.1）
- **有质量保障** → RAGAS 评估 + CI 门禁（5.3）

> 学习心法：后面每一个技术点，都问自己"它服务于上面哪个问题"。脱离业务问题的技术细节记不住，锚定业务的才能内化。

## 1.3 架构总览（背下来）

```
┌────────────────────────────────────────────┐
│  Vue3 前端（人用）      MCP 客户端（AI 用）  │
│  对话/可视化/文档管理    Claude/Cherry Studio│
└────────────┬───────────────────┬───────────┘
             │ REST + JWT        │ MCP(stdio)
┌────────────▼───────────────────▼───────────┐
│            API 服务层 (FastAPI)             │
│  请求 → 鉴权 → 日志/Trace → 业务逻辑        │
│  数据管线：队列 → 状态机 → 去重 → 入库      │
└────────────────────┬───────────────────────┘
                     │ 进程内直连
┌────────────────────▼───────────────────────┐
│              RAG 引擎层                     │
│  检索：缓存 → 混合检索 → RRF → 重排         │
└────────────────────┬───────────────────────┘
┌────────────────────▼───────────────────────┐
│  存储：Chroma(向量) SQLite(注册表/用户)      │
│        FAISS(语义缓存) data/docs(原文件)    │
└────────────────────────────────────────────┘
```

**关键分层原则**：引擎层不知道 HTTP/鉴权/日志的存在；API 层不知道检索算法细节。MCP 和 REST 两个入口复用同一个引擎——这就是分层的 payoff。

## 1.4 技术栈地图（每项技术的角色）

| 技术 | 角色 | 没有它会怎样 |
|------|------|-------------|
| LangChain | 文档加载/切分的工具库 | 自己写各格式解析器 |
| BGE embedding | 文本 → 向量（中文优化） | 无法做语义检索 |
| Chroma | 向量存储 + 相似度检索 | 自己管理向量+算距离 |
| jieba | 中文分词 | BM25 对中文失效 |
| rank_bm25 | BM25 算法实现 | 关键词检索路线缺失 |
| CrossEncoder (BGE) | 精细重排 | Top1 准确率停在 66.7% |
| FAISS | 语义缓存的向量索引 | 换个问法就无法命中缓存 |
| FastAPI | 异步 Web 框架 | 无法服务化/流式/鉴权 |
| Vue3 | 前端 SPA | 用 Streamlit（无法做真正产品） |
| RAGAS | RAG 评估框架 | 质量靠感觉 |
| structlog | 结构化日志 | 线上问题靠猜 |
| Langfuse | LLM 链路追踪 | token 成本黑盒 |
| FastMCP | MCP 协议实现 | AI 客户端无法接入 |

# 第二章：前置概念补课

> 如果这些概念你已经熟，跳到 2.7「概念之间的协作图」自测一下即可。

## 2.1 Embedding（向量化）

**是什么**：把一段文本映射成一个高维向量（本项目 768 维），语义相近的文本在向量空间里距离近。"怎么退货"和"退货流程"的向量很近，尽管字面只有两个字相同。

**为什么需要**：精确匹配（SQL LIKE / 关键词）无法处理"换了说法"的查询。向量检索解决**语义泛化**。

**关键限制**（理解后面所有设计的钥匙）：
- 对**生僻专有名词/型号/缩写**不敏感——训练语料里没见过的词，向量空间里是"模糊的一团"。这就是必须保留 BM25 的原因。
- embedding 是"各自编码"的：问题和文档分别变向量再算距离，精度有天花板。这就是需要 CrossEncoder 的原因。

**本项目的位置**：`rag_engine/embedder.py`，本地 BGE 模型（`bge-base-zh-v1.5`），单例懒加载。

**验证方法**（实验 1 会做）：两个语义相同字面不同的句子，算余弦相似度，看是不是明显高于无关句对。

## 2.2 向量检索（ANN 近似最近邻）

**是什么**：拿查询向量在库里找"距离最近"的 Top-K 个片段。Chroma 内部用 HNSW 索引——一种近似算法，牺牲一点点精度换数量级的速度提升（全量比对在百万片段下不可行）。

**一句话理解 HNSW**：像跳表一样的多层"高速公路"，先在粗层大步跳到大致区域，再在细层精确定位。

## 2.3 BM25（关键词检索）

**是什么**：经典文本检索算法（ Elasticsearch 的核心），本质是"改良版词频统计"：一个词在这篇文档出现越多、且在全库越罕见，得分越高。

**为什么中文要 jieba**：BM25 以"词"为单位，中文没有空格。"知识库管理系统"不切词就是一个 token，查"管理系统"永远匹配不上。

**它和向量检索的互补**（必考）：

| | 向量检索 | BM25 |
|---|---------|------|
| 擅长 | 语义改述、口语化问法 | 专有名词、型号、缩写、精确术语 |
| 弱点 | 生僻词不敏感 | 换说法就失效 |
| 原理 | 语义空间距离 | 词频统计 |
| 可解释性 | 弱（黑盒） | 强（能看到哪个词命中） |

## 2.4 RRF（Reciprocal Rank Fusion 排名融合）

**要解决的问题**：向量检索和 BM25 各返回一个列表，怎么合并？

**为什么不能按分数加权**：两路分数**不可比**——余弦相似度 ∈ [-1,1]，BM25 分数无上界。拿身高和体重加在一起没有意义。

**RRF 的思路**：不看分数，只看**排名**。每个片段的得分 = Σ 1/(k + rank)，k=60（业界平滑常数，压低头部排名的权重差异）。在两路都靠前的片段必然胜出。

**优点**：零调参、对分数分布不敏感。**代价**：丢失了分数里的确信度信息——但有重排兜底，召回阶段无所谓。

## 2.5 CrossEncoder 重排（两阶段漏斗）

**召回 vs 精排的分工**：

```
几千个片段 --[向量+BM25 便宜快]--> 几十个候选 --[CrossEncoder 贵但准]--> Top-K
           召回：宁多勿漏              精排：宁缺毋滥
```

**CrossEncoder 和 embedding 的本质区别**：
- embedding（双塔/Bi-Encoder）：问题和文档**分别**编码 → 算距离。快（文档向量可预先算好），但两者编码时互相看不见，精度受限。
- CrossEncoder：问题和文档**拼在一起**过模型 → 直接输出相关性分。准（交叉注意力看到词级互动），但每个候选都要一次完整推理，无法预计算。

**本项目实测**：重排让 Top1 准确率 66.7% → 100%。这就是"两阶段漏斗"的价值。

## 2.6 语义缓存（LRU + FAISS 两级）

**LRU 精确缓存**：问过一字不差的问题 → 字典查表 → 0.3ms 返回。
**FAISS 语义缓存**：把新问题向量化，和历史查询的向量算余弦相似度，> 0.92 判定"同一个问题的不同问法" → 复用答案。

**为什么阈值 0.92 这么高**：缓存错误是**放大**的错误——一次误命中，之后所有相似问题都错。宁漏判（走正常检索，损失性能）不误判（返回错答案，损失正确性）。

**为什么这是性能皇冠**：命中后 embedding 计算、向量检索、BM25、重排**全部跳过**，首查 2.4s → 0.3ms。

## 2.7 概念协作图（自测：能默画出来吗）

```
query ──► ①LRU查表 ──命中──► 返回
            │未命中
            ▼
        ②query向量化 ──► ③FAISS语义缓存查相似度 ──>0.92──► 返回
            │未命中                              （跳过④⑤⑥）
            ▼
   ④向量检索(Chroma)   ⑤BM25检索(jieba)
        └──────┬──────┘
               ▼
        ⑥RRF融合（按排名）
               ▼
        ⑦CrossEncoder重排（Top候选精排）
               ▼
        ⑧写缓存 + 返回Top-K
```

# 第三章：RAG 引擎层精讲

> 代码目录：`rag_engine/`。这层是"算法核心"，不含任何 Web 概念。

## 3.1 loader.py — 多格式加载

**职责**：按后缀分发到对应解析器（pdf/md/docx/txt），统一输出 LangChain Document 列表。

**必须知道的坑**（真实踩过，见 development-issues.md P01）：
LangChain loader 会自动把**完整文件路径**写进 `metadata["source"]`。这导致：
- 注册表用纯文件名做 key，两者对不上
- `setdefault("source", ...)` 静默失效（key 已存在）
- 同名文档替换更新时删除失效 → 旧片段残留

**修复**：入库时**强制赋值** `doc.metadata["source"] = source`。

**学习要点**：第三方库写入的元数据，覆盖用赋值不用 setdefault；"静默失败"比报错更危险。

## 3.2 splitter.py — 递归切分

**参数**：chunk_size=500 字符，overlap=50，中文分隔符优先（\n\n → \n → 。→ 空格）。

**递归切分的逻辑**：优先按最粗的分隔符（段落）切；段落超长才降级用句子切；还超长才按字符硬切。这样切出来的片段尽量保持语义完整。

**为什么需要 overlap（重叠）**：一句话正好跨在两个片段边界上时，不重叠就两边都不完整。50 字重叠保证边界信息至少完整出现在一个片段里。

**为什么是 500/50**（实验对比过 300 vs 600）：
- 太小（300）：单个片段信息量不足，答案需要的证据被切碎，且片段数暴涨
- 太大（600）：一个片段混多个主题，向量表示被"稀释"，检索精度下降；上下文 token 浪费

**重要的认知**：最优参数**和文档类型强相关**（法律条文条目短 vs 操作手册步骤连贯），统一参数是简化，不是最优解。

## 3.3 embedder.py — 向量化

**设计模式**：单例 + 懒加载 + 双检锁（double-checked locking）。

**为什么懒加载**：模型加载要几秒~几十秒，import 时就加载会拖慢一切依赖它的模块（包括跑个单元测试都要等）。
**为什么双检锁**：多线程并发首次调用时，保证只加载一次（先无锁检查快路径，拿锁后再检查一次）。
**为什么强制离线模式**：`HF_HUB_OFFLINE=1`，防止运行时偷偷联网检查更新导致服务不稳定。

**API/本地双模**：走 API（OpenAI 兼容）或本地 BGE，配置切换。选型逻辑见 7.6。

## 3.4 vectorstore.py — Chroma 封装

**职责**：片段的增删查 + 按 source（文档名）批量删除。

**为什么需要"按文档删除"**：替换更新、文档下架，都以文档为单位操作。这也是 source 元数据必须干净统一的原因（见 3.1 的坑）。

**为什么用 get_all**：去重索引重建、BM25 重建、注册表对账，都需要"全量片段"作为事实源。

## 3.5 retriever.py — 混合检索核心（本项目最核心文件）

**主流程**：就是 2.7 的协作图，对应 `retrieve()` 方法。

**四个关键工程细节**：

1. **BM25 延迟构建**：BM25 索引在首次检索时才建（冷启动加载文档+分词很慢），且有脏标记——文档变更后置脏，下次检索重建。为什么不做实时重建？入库后不一定马上有人查，延迟到"需要时"再付这个成本。

2. **查询向量预编码复用**：语义缓存检查和向量检索都需要 query 向量，编码一次传两处，省一半 embedding 计算。

3. **`last_cache_hit` 属性**：暴露本次检索的缓存命中情况（exact/semantic/None）给上层观测——可观测性从引擎层就开始设计，不是 API 层补的。

4. **重排可降级**：未配置 reranker 模型时自动跳过重排，系统仍可用（召回质量降低但功能完整）。

**必须理解的输出结构**：检索结果带 `source`（来源文档）+ 分数 + 阶段信息。四阶段详情接口（`retrieve_with_details`）能分别返回向量/BM25/RRF/重排四个列表——这不只是炫技界面，是**排障工具**（见 6.1）。

## 3.6 cache.py — 两级查询缓存

**结构**：LRU 字典（精确）+ FAISS 索引（语义）+ 线程锁。

**三个必知点**：
1. **写入的粒度**：缓存的是"query → 检索结果"（不是生成的答案——答案缓存和上下文、模型参数相关，复杂度高）。
2. **clear() 的由来**：修缓存一致性 bug 时新增的方法——入库/删除后必须清缓存，否则返回过期数据（详见 7.9）。
3. **线程安全**：FastAPI 线程池 + 后台 worker 都可能并发读写缓存，所有操作持锁。

# 第四章：API 服务层精讲

> 代码目录：`api/`。这层把"算法引擎"变成"企业服务"。

## 4.1 main.py + deps.py + services.py — 骨架

**main.py**：应用入口。lifespan 里做三件事——模型预热（避免首个请求超时）、注册表与向量库对账（历史文档纳管）、优雅关闭。中间件链：请求 ID 注入 → 鉴权 → 日志。

**deps.py**：引擎单例依赖注入。FastAPI 的 Depends 机制让路由函数声明式地拿到引擎实例，测试时可替换。

**services.py**（最值得精读）：核心命题是**"同步引擎 × 异步框架"的适配**：
- 阻塞操作（embedding 推理/Chroma/重排）→ `asyncio.to_thread` 扔线程池，事件循环不被卡死
- LLM 调用 → AsyncOpenAI 客户端单例（连接池复用 + 真异步）
- **为什么必须这么做**：异步框架里直接调阻塞代码，一个 2 秒的检索会挂起**所有**并发请求。这是 Python 异步工程的第一课。

**多轮对话记忆**：最近 3 轮原文 + 更早的 LLM 摘要压缩。为什么 3 轮：原文保留细节（指代消解需要），摘要保留宏观（话题/结论），上下文长度恒定。
**关键设计**：检索用**当前问题**的向量，不带历史——历史只用于让 LLM 理解指代，不应污染查询向量。

## 4.2 auth.py + routers/auth.py — 双通道鉴权

**双通道**：

| | JWT | API Key |
|---|-----|---------|
| 给谁用 | 人（Web 前端） | 系统（脚本/服务集成） |
| 获取方式 | 登录交互换取 | 创建时一次性展示 |
| 生命周期 | 12h 过期 | 长期，可吊销 |
| 存储 | 前端 localStorage | 调用方自管 |

**安全细节**（每个都有明确理由）：
- 密码 PBKDF2-SHA256 + 随机盐 + 10 万次迭代：慢哈希让暴力破解成本极高；盐让相同密码哈希不同（防彩虹表）
- API Key 只存 SHA256 哈希 + 16 字符前缀：库里泄露也还原不出；前缀用于列表识别
- 常数时间比较（`secrets.compare_digest`）：防止通过响应时间差异逐字节猜 Key
- **JWT_SECRET 未配置时每次启动随机轮换**：重启全员掉线——这是"安全降级"设计：宁可不可用，不可不安全
- 首个注册用户自动 admin：Bootstrap 机制，解决"第一个管理员从哪来"

## 4.3 数据管线三件套：dedup.py + registry.py + worker.py

**registry.py（状态机）**：SQLite 存每份文档的状态 `pending → parsing → available / duplicate / failed`。

为什么需要状态机（三个理由）：
1. 用户体验：上传后能看到"解析中/可用/失败（带原因）"，而不是黑盒等待
2. 一致性裁决：注册表 vs 向量库是双存储，对账机制以向量库为事实源修正漂移
3. 审计：什么时间入库了什么、结果如何

**dedup.py（双重去重）**：
- **文件级 SHA256**：整文件字节一致 → 直接跳过（重复上传零成本处理）
- **片段级 SHA256**：切分后逐片段比对，跨文档的重复内容（如相同的免责声明）只存一份
- 片段哈希**持久化在向量库元数据**里：服务重启不丢，索引可从数据全量重建（"数据是事实源，索引可再生"原则）

**worker.py（摄入工作线程）**：内存队列 + 单线程串行。

**为什么串行（重要设计）**：Chroma 写入无并发保护，多线程同时写会数据错乱。正确性 > 吞吐。
**为什么不上 Celery**：单机部署 + 单线程够用 + 多 worker 依然解决不了 Chroma 并发写。但接口按任务队列语义抽象（submit/get_task），量级上来换后端时上层不动。（完整决策过程见 7.10）

**摄入八步**（完整版见 6.2）：注册 pending → 入队 → 文件级去重 → 同名替换判断（删旧）→ 解析切分 → 片段级去重 → 向量化入库 + 重建 BM25 + **清查询缓存** → 状态落定（失败则回滚标记 failed）。

## 4.4 observability.py — 可观测性

**三件套**：
1. **structlog 结构化日志**：事件都是带字段的数据（`retrieval_done` 带 query/latency/cache_hit），开发彩色控制台 / 生产 JSON 一行一条（ELK 直采）
2. **请求 ID 中间件**：每请求生成唯一 ID，contextvars 自动注入该请求的所有日志——用户报障时拿 ID 还原完整现场
3. **Langfuse Tracer**：trace 层级（chat → retrieval + generation），记录 token 用量/延迟；**未配置 keys 时零开销降级为 no-op**（可观测组件不能成为可用性依赖）

**必须理解 contextvars 的坑**（真实踩过 P20）：
contextvars 是 copy-on-write 的任务隔离机制——依赖函数里 `bind(user=...)` 发生在中间件的**子任务**里，父任务（中间件）看不到。解法是双写：`request.state.user`（跨任务显式传递）+ contextvars（供业务日志）。另：中间件打日志必须在 `clear_contextvars()` **之前**，顺序反了日志字段就丢。

# 第五章：其他模块

## 5.1 Vue3 前端（frontend/）

**结构**：views 四页（Chat / SearchViz / Documents / ApiKeys）+ Pinia（JWT 状态）+ axios 拦截器（401 统一登出）+ 路由守卫。

**最有学习价值的一点——SSE 流式的正确姿势**：
浏览器原生 `EventSource` **只支持 GET 且不能自定义请求头** → 带鉴权的 POST SSE 接口用不了。
解法：`fetch` + `ReadableStream` 手写 SSE 解析（按空行分帧、解析 event:/data: 行、处理末帧不完整的缓冲区）。见 `frontend/src/api/sse.js`。

**为什么用 Vite 开发代理**：请求发给同源的开发服务器再转发后端，绕开跨域；等价于生产的 nginx 反代。

## 5.2 MCP Server（mcp_server/server.py）

**MCP 协议是什么**：AI 客户端与工具之间的标准协议（"AI 世界的 USB 接口"）。客户端里的大模型**自主决定**何时调用哪个工具——用户说"查下报销流程"，模型自己判断要调 `search_knowledge`。

**6 个工具**：search_knowledge / ingest_document / list_documents / delete_document / web_search（DuckDuckGo）/ get_time。

**启动时预加载模型**：MCP 工具调用有超时限制，首次调用才加载 embedding（几十秒）必超时——预热挪到启动阶段。

**MCP 与 REST 的关系**：同一引擎的两个入口，面向不同消费者（AI 客户端 vs 传统系统）。不是重复建设。

## 5.3 评估体系（evaluation/runner.py）

**流水线**：25 题测试集 → 逐题跑完整 RAG 管线 → RAGAS 四指标（LLM-as-Judge）+ 负样本拒答率 → 报告落盘 → 门禁判断（低于阈值 exit 1）。

**RAGAS 四指标的含义**（必须能用自己的话讲）：
- **faithfulness 忠实度**：答案的每句陈述是否被检索上下文支持（反幻觉核心指标）
- **answer_relevancy 答案相关性**：答案是否切题（防答非所问）
- **context_precision 上下文精确率**：检索回来的片段里，相关的排不排得靠前
- **context_recall 上下文召回率**：标准答案需要的信息，检索有没有找全

**测试集分层设计**（25 题）：专有名词类（测 BM25）/ 语义改述类（测向量）/ 跨文档混淆类（测重排）/ 负样本 5 题（测拒答）。分层的价值：指标掉了能**定位是哪类能力退化**。

**工程上处理过的坑**（细节见 development-issues.md P07-P15）：judge 输出截断（放宽 max_tokens）、并发限流全 nan（降并发+重试）、**单个 nan 毒化整列均值**（nanmean 语义 + nan 率>30% 判评估不可信）、阈值先跑基线再定（留 10% 余量）。

**最终基线**：faithfulness 0.71 / relevancy 0.74 / precision 0.89 / recall 0.75 / 拒答率 0.80。

# 第六章：两条核心流程走读

## 6.1 流程一：用户问"什么是混合检索"到收到答案

```
1. Vue3 前端发 POST /api/v1/chat（带 JWT + 历史 + 问题）
2. 中间件：生成 request_id=abc123，绑定日志上下文
3. 鉴权依赖：校验 JWT → user=demouser，双写 request.state + contextvars
4. services.chat()：
   a. cache 检查（LRU 精确 → FAISS 语义）
      命中 → 直接拿片段跳到 e（此时缓存命中日志 cache_hit=exact/semantic）
   b. 未命中 → to_thread{ retriever.retrieve() }：
      query 向量化（预编码，缓存检查+向量检索共用）
      → Chroma 向量检索 Top-N（结果列表 A）
      → BM25 检索 Top-N（jieba 分词，结果列表 B）
      → RRF 融合 A+B（按排名，k=60）
      → CrossEncoder 重排融合候选（结果列表 C）
      → 写两级缓存
   c. 组装上下文：C 的 Top-K 片段编号 [1][2][3] + 来源
   d. 历史：最近 3 轮原文 + 更早摘要
   e. AsyncOpenAI 流式生成（提示词要求"仅依据资料+引用编号"）
   f. SSE 逐 token 推给前端（sources 事件 → delta 事件流 → done 事件）
5. 全程日志：retrieval_done（latency/cache_hit/sources）→ generation_done
  （token_usage）→ chat_done → http_request，全部带 request_id=abc123
6. Langfuse（若配置）：chat trace → retrieval/generation 子 span
```

**流式版**：非流式 `/chat` 一次返回；流式 `/chat/stream` 用 SSE——前端先收到来源列表（可先渲染引用区），再逐字渲染答案（打字机效果），首字延迟大幅下降。

**排障视角**（这是四阶段可视化接口存在的意义）：用户说"回答不对"时，用 `/search/details` 看四个列表：
- 列表 A 对 B 错 → 向量检索找到但 BM25 没找到（正常，互补）
- A、B 都有正确片段但 RRF 后掉出前列 → 融合参数问题
- RRF 前列正确但重排后掉下去 → reranker 问题（或该片段与 query 语义确实远）
- 全都对但答案错 → 生成环节问题（上下文组装/提示词/模型能力）
**每层错误的修复手段完全不同**——这就是为什么要把检索过程拆开看。

## 6.2 流程二：一篇 PDF 从上传到可检索

```
1. POST /api/v1/documents（multipart 文件）→ 鉴权 → 文件名清洗（防路径穿越）
   → 类型白名单校验 → 落盘 data/docs/ → 注册表登记 pending
   → 入队 → 立即返回 202 + task_id（前端开始轮询）
2. Worker 线程取出任务：状态 → parsing
3. 文件级去重：整文件 SHA256 在已知集合？→ 是：duplicate，结束
4. 替换判断：同名文档已存在且内容不同？→ 是：删除旧片段 + 去重索引同步
   （避免旧哈希残留导致新版本片段被误判重复）
5. 解析（按后缀选 loader）→ 切分（500/50）→ source 元数据强制覆盖
6. 片段级去重：逐片段 SHA256 比对，重复的丢弃
7. 批量向量化 → 写入 Chroma（带 source/chunk_id/hash 元数据）
   → BM25 索引置脏 → **清空查询缓存**
8. 状态 → available（chunks 数入册）
   任何步骤异常：回滚已写入向量 → failed + 错误原因
9. 前端轮询到 available → 文档列表刷新，此刻起可被检索
```

**为什么第 7 步必须清缓存**：不清的话，"上传前查过的查询"会命中旧缓存，新内容不可见；删除同理（更严重：删掉的内容从缓存返回）。这是本项目最经典的 bug，详见 7.9。

# 第七章：十个设计决策专题

> 每个决策都是"问题 → 备选方案 → 选择及理由 → 代价"。吃透 = 能复述这个结构。

## 7.1 为什么混合检索而不是单路向量？

数据说话：25 题测试集，混合命中率比单路向量 **+8.3%**。两类查询各自打爆对方：语义改述（向量赢）、专有名词（BM25 赢）。互补召回是本质，不是堆技术。

## 7.2 为什么 RRF 而不是分数加权？

两路分数不可比（[-1,1] vs 无上界），加权要么无意义要么引入难调的权重参数。RRF 零调参、看排名不看分数。代价是丢确信度信息——有重排兜底。

## 7.3 为什么重排只处理小候选集？

CrossEncoder 每个候选一次完整前向推理，全量跑延迟不可用。两阶段漏斗：便宜的召回缩到几十，贵的精排只处理这几十。收益：Top1 66.7% → 100%。

## 7.4 为什么缓存阈值 0.92 而不是 0.85？

缓存错误是放大的错误（一次误命中 → 所有相似问题全错）。高阈值 = 宁漏判不误判：漏判的代价只是走一遍正常检索（几百 ms），误判的代价是错误答案（业务事故）。

## 7.5 为什么切分 500/50？

实验对比 300/600 后的均衡点。300：证据被切碎+片段数暴涨；600：多主题稀释向量+token 浪费。**但最优参数随文档类型变化**，统一值是简化。

## 7.6 为什么 embedding 用本地模型？

① 数据不出内网（企业硬需求）② API 按 token 计费 vs 本地一次性投入 ③ 模型版本自控（API 升级导致向量分布漂移，缓存和基线全失效）。代价：效果天花板略低 + 自己扛部署。做成可配置：数据敏感用本地，效果敏感用 API。

## 7.7 为什么 SQLite 而不是 PostgreSQL？

当前量级零运维、单文件备份即复制。但这是**有意识的过渡**：知道边界（库级写锁、多进程瓶颈），访问层薄封装，迁移时只换连接。选型成熟度 = 知道什么时候该换。

## 7.8 为什么任务队列不上 Celery？

① Chroma 无并发写保护，多 worker 写坏数据（正确性优先）② 一天几十份文档用不着分布式队列 ③ 单进程部署，Celery 的 broker/worker/监控三件套是纯负担。但接口按任务队列语义抽象——量级到了换后端，上层零改动。

## 7.9 为什么写路径必须清缓存？（最经典的一课）

**事故**：删除文档后，旧内容仍从缓存返回，且因为缓存命中延迟极低，看起来"系统反应很快"——数据幽灵。
**根因**：写路径清理了向量库/BM25/去重索引三处，漏了第四处（查询缓存）。每个组件单独都对，组合错了。
**方法论**：**带读缓存的系统，写路径要做"失效清单"**——本项目清单五处：向量库、BM25、去重索引、注册表、查询缓存。逐项核对。
**发现方式**：单元测试发现不了（要构造"写后读同一查询"的时序），端到端回归测试才抓得住。

## 7.10 为什么"接口先抽象、实现后置"是架构演进的正确姿势？

Celery 决策（7.8）和 SQLite 决策（7.7）共同的模式：**当前约束下选最简单的实现，但接口按未来的形态设计**。这样演进 = 换实现（局部），而不是改架构（全局）。反面是"过度设计"：为想象中的量级提前支付复杂度，且大概率用不上。

# 第八章：动手实验

> 学习铁律：**看会 ≠ 会**。以下实验都在"破坏"某些东西，观察系统的反应——这是理解设计意图最快的方式。均在 rag conda 环境下进行。

## 实验 1：验证 embedding 的语义能力（理解 2.1）

```python
from rag_engine.embedder import Embedder
import numpy as np
a = Embedder.embed_query("怎么退货")
b = Embedder.embed_query("退货流程是什么")
c = Embedder.embed_query("今天天气怎么样")
cos = lambda x, y: np.dot(x, y) / (np.linalg.norm(x) * np.linalg.norm(y))
print(cos(a, b))  # 预期 > 0.85（语义相近）
print(cos(a, c))  # 预期明显更低
```
**观察点**：字面只有"退货"两个字相同，相似度却很高——这就是向量检索能处理"换说法"的原因。

## 实验 2：对比缓存命中 vs 未命中的延迟（理解 2.6）

启动 API 后，同一问题连问两次，看响应时间（Swagger 或前端都有耗时显示；或看日志 `retrieval_done` 的 latency）。
**观察点**：第二次毫秒级且日志 `cache_hit=exact`。再换个说法问（"XX 的流程是什么样"），可能触发 `cache_hit=semantic`。

## 实验 3：观察四阶段检索差异（理解 3.5）

## 实验 4：验证替换更新（理解 4.3）

上传 A.txt（内容 v1）→ 确认可检索 → 修改内容为 v2 → 同名再上传 → 检索 v1 的独有关键词。
**观察点**：v1 内容检索不到了（旧片段被删），v2 内容排第一。**再试**：改回 v1 再传——注意观察片段级去重生效（v1 片段哈希库里其实已删，会正常入库；但如果你上传另一份包含相同段落的**不同**文档，重复片段会被跳过）。

## 实验 5：验证缓存一致性修复（理解 7.9，重现经典 bug）

# 第十章：常见误解澄清

**误解 1："重排提升了检索能力"**
重排不改变召回（该找到的召回阶段就找到了），它提升的是**排序质量**——把已经在候选集里的正确片段排到第一。Top1 66.7%→100% 的含义是：正确片段本来就在 Top-K 里，重排把它顶到了第一位。

**误解 2："缓存是优化，不影响正确性"**
缓存是**一致性风险点**。7.9 的经典 bug 就是证据——每个组件单独正确，组合后数据幽灵。任何"加缓存"的改动，都要同步设计"失效策略"。

**误解 3："语义缓存和向量检索是一回事"**
都用向量+相似度，但对象不同：向量检索比"问题 vs 文档片段"（找资料），语义缓存比"问题 vs 历史问题"（找问过的人）。阈值语义也不同：检索要召回（阈值低些），缓存要精确（0.92 宁缺毋滥）。

**误解 4："混合检索就是为了提高准确率"**
更准确说是**扩大能力覆盖面**：单路向量在专有名词类查询上有盲区，单路 BM25 在语义改述上有盲区。混合 = 两者盲区互补，然后交给 RRF+重排裁决。

**误解 5："评估指标高 = 系统好"**
前提是**评估本身可信**：测试集有代表性（25 题分层设计）、judge 没截断/限流、nan 率可控。nan 率 30% 门禁的存在就是因为"指标漂亮但评估坏了"比"指标难看"更危险。

**误解 6："异步化就是加 async 关键字"**
同步阻塞代码加 async 前缀依然是阻塞的（甚至更糟，伪装成异步）。真正的异步化是分情况处理：阻塞推理→线程池，LLM→真异步客户端，重操作→后台任务。见 4.1。

**误解 7："MCP 和 REST API 是两套系统"**
一个引擎、两个协议入口。REST 给传统系统（显式调用），MCP 给 AI 客户端（模型自主调用）。改检索逻辑只改引擎，两个入口同时受益——这正是分层的价值。

**误解 8："SQLite/单线程/无 Celery = 不够专业"**
工程成熟度是**匹配真实约束**而不是堆技术。Chroma 无并发写保护下，单线程串行是唯一正确解；接口已按队列语义抽象，演进只需换实现。为想象中的量级提前支付复杂度，是过度设计不是专业。
