## 一、项目定位与全局

### Q1：用一分钟介绍这个项目

**答**：这是一个企业级智能知识库平台，解决的核心业务问题是：企业内部有大量文档（制度、手册、FAQ），员工或客户想问问题时，要么翻不到、要么翻到了看不懂全文。我的方案是把文档变成"可问答、可溯源的知识服务"。

整体分四层：最底层是 RAG 检索引擎，做混合检索加缓存；往上是 FastAPI 服务层，提供检索、流式对话、文档管理的异步接口，并带鉴权、数据管线和全链路日志；再往上是 Vue3 前端；另外一条线是把 RAG 能力封装成 6 个 MCP 标准工具，让 Claude Desktop、Cherry Studio 这类 AI 客户端可以直接调用，所以是 REST API + MCP 双交付形态。

质量上有一套 RAGAS 自动化评估接在 CI 里做门禁。关键数据：重排让 Top1 准确率从 66.7% 提到 100%，混合检索比单路向量命中率提升 8.3%，缓存命中的查询延迟从秒级降到 0.3 毫秒。

【深挖】为什么做双交付形态？→ 见 Q5。

### Q2：这个项目解决什么业务痛点？目标用户是谁？

**答**：痛点有三个：一是**知识获取效率**——员工问"报销流程是什么"，传统方式是翻 Confluence 或问 HR，平均要几分钟到几小时；二是**知识可信度**——直接问通用大模型会幻觉，业务场景不能接受；三是**知识时效**——文档更新后，问答系统如果不同步，会给过期答案。

目标用户两类：企业内部员工（查制度、查产品文档），以及外部客户（智能客服场景）。两种用户的接入方式也不同：内部走 Web 前端，外部系统集成走 API Key。

### Q3：为什么用 RAG，而不是微调模型？

**答**：这是个典型的选型问题，我从四个维度对比过：

1. **知识更新成本**：微调后知识固化在权重里，文档一改就要重新训练，周期以天计；RAG 只需重新入库，分钟级生效。企业文档是高频变更的，这点是决定性的。
2. **可溯源**：RAG 的回答能标注"依据哪份文档哪一段"，出了问题能定位；微调模型是黑盒，没法审计。这在合规要求高的场景（法务、金融）是硬需求。
3. **权限控制**：RAG 可以按文档粒度控制检索范围（谁能查到哪份文档），微调做不到——知识进了权重，谁都能问出来。
4. **成本**：微调要 GPU 资源和数据标注；RAG 用现成模型加检索设施，成本主要在向量化和存储。

微调更适合改变"风格和格式"（比如让模型学会某种输出规范），而不是注入"事实知识"。所以事实型知识用 RAG，行为型能力才考虑微调，两者不冲突。

### Q4：项目的整体架构是怎么分层的？为什么这样分？

**答**：四层，从上到下：前端（Vue3）→ API 服务层（FastAPI）→ RAG 引擎层 → 存储层（Chroma 向量库 + SQLite + FAISS 缓存索引），MCP Server 作为旁路入口同样落在引擎层之上。

分层的关键考虑是**引擎与服务解耦**：RAG 引擎（检索、切分、向量化）不感知 HTTP、鉴权、日志这些事；API 层负责把同步引擎异步化、加鉴权、埋观测点。这样做的好处是 MCP Server 和 REST API 两个入口复用同一套引擎，将来换前端、加客户端都不动核心逻辑。

### Q5：为什么做 REST API 和 MCP 双协议？不重复吗？

**答**：两种协议面向不同消费者，不重复。

REST API 面向**传统系统集成**——前端、其他后端服务、脚本，这是标准的服务间通信方式，带完整的鉴权、流式、错误码语义。

MCP 面向**AI 原生客户端**——Claude Desktop、Cherry Studio 这类工具的特点是"由大模型自主决定何时调用工具"。用户不会显式调接口，而是说"帮我查一下报销流程"，模型的 Agent 能力自己判断要调 search_knowledge。MCP 是这个生态的标准化协议（可以理解为"AI 世界的 USB 接口"），我封装了 6 个工具：检索、入库、文档列表、删除、联网搜索、时间查询。

业务价值在于：同一份知识资产，既能服务传统系统，也能服务未来的 AI 工作流，不需要做两套后端。

### Q6：项目里你觉得最有技术含量的设计是什么？

**答**：如果只能选一个，我选**质量保障体系**。因为检索引擎的组件（混合检索、重排、缓存）都是业界成熟方案，拼起来不难；难的是**你怎么知道它好不好、改了之后有没有变差**。

我做了三层：一是对比实验（单路 vs 混合、有无重排、缓存收益），拿到量化基线；二是 RAGAS 自动化评估，用忠实度、相关性、检索精确率/召回率加负样本拒答率五个指标持续测量；三是把这些指标做成 CI 门禁——低于阈值自动拦截合并，质量从"感觉没问题"变成"机器说了算"。这套东西让项目从 demo 变成了可维护的工程。

## 二、核心流程：一次提问背后发生了什么

### Q7：完整描述用户问一个问题到收到回答的全流程

**答**：以对话场景为例，分六个步骤：

1. **鉴权**：请求带 JWT 或 API Key 进来，服务层校验身份，同时生成一个请求 ID 贯穿全程。
2. **查询缓存检查**：先查两级缓存——LRU 精确缓存（问过一字不差的问题直接命中，0.3ms）和 FAISS 语义缓存（把问题向量化，和历史查询算余弦相似度，超过 0.92 阈值判定为"同一个问题的不同问法"）。命中任何一级就直接返回，跳过后面所有环节。
3. **混合检索**：未命中缓存，先编码问题向量，然后并行做两路——向量检索（Chroma，找语义相近的片段）和 BM25 检索（关键词精确匹配，对专有名词、型号、缩写这类查询强）。
4. **融合与重排**：两路结果用 RRF（排名倒数融合）合并成候选集，再过 CrossEncoder 重排——它是"问题+片段"一起精细打分的模型，比向量检索的"先各自编码再算距离"精度高。
5. **生成回答**：把 Top-K 片段编号后拼进提示词，要求模型"仅依据资料回答，标注引用编号"，走流式接口逐字返回前端。多轮对话场景，最近 3 轮原文保留，更早的用 LLM 压缩成摘要，控制上下文长度。
6. **记录与缓存**：全链路每个环节的延迟、命中情况、来源文档都写结构化日志（Langfuse 配置了的话同时记录 trace），检索结果写回缓存供下次命中。

### Q8：为什么要做两级缓存？一级不够吗？

**答**：两级解决的是两类不同的"重复提问"：

- **LRU 精确缓存**处理"一字不差的重复"——客服场景里 20% 的问题占了 80% 的流量，"怎么退货"每天被问几百次，这种精确命中是 O(1) 查表。
- **语义缓存**处理"换了说法的重复"——"怎么退货"和"退货流程是什么"字面完全不同，精确缓存失效，但语义上是同一个问题。用向量相似度 0.92 的阈值判定，可以复用答案。

业务收益直接体现在延迟和成本上：首查 2.4 秒（含模型推理），语义命中约 3 毫秒，精确命中 0.3 毫秒，同时省掉了 embedding 计算、检索和重排的 GPU/CPU 开销。

【深挖】语义缓存会不会"错命中"？会，所以阈值定在 0.92 这种偏保守的水平，宁可漏判（走正常检索）也不误判（返回错误答案）。缓存错误是"放大"的错误——一次错，之后所有相似问题都错，所以这个环节宁可保守。

### Q9：为什么检索要做"向量+BM25+重排"这么复杂？单路向量不行吗？

**答**：这是我在项目里用数据验证过的问题。我做了 25 题的测试集，按问题类型分了四类，结论很清晰：

- **语义改述型问题**（"怎么让机器听懂人话"→语音识别文档）：向量检索强，BM25 弱——字面几乎不重叠。
- **专有名词/型号/缩写类问题**：BM25 强，向量弱——通用 embedding 模型对生僻术语的语义空间不够准，反而关键词精确匹配稳。
- **跨文档易混淆问题**：单路都容易错，靠混合加召回量再重排解决。

实测数据：混合检索命中率比单路向量高 8.3%。所以两路混合的本质是**互补召回**——各自覆盖对方的盲区。

重排解决另一个问题：召回阶段为了快，用的是"粗粒度"的相似度（向量各自编码后算距离），而 CrossEncoder 是把问题和候选片段拼在一起精细打分，代价是慢，所以只对融合后的 Top 候选做。两阶段是"先广撒网再精挑"的漏斗。实测重排让 Top1 准确率从 66.7% 提到 100%。

### Q10：回答里的引用标注是怎么实现的？业务价值是什么？

**答**：机制上，检索出的片段在拼进提示词前就编好号（[1][2][3]），提示词明确要求模型引用时用编号标注，回答返回后把编号映射回原文档名和片段内容，前端展示成可点击的来源列表，用户能点开看原文。

业务价值是**可信与可审计**：用户对 AI 回答的天然疑虑是"这是编的还是真有依据"，引用标注把回答锚定到具体文档；一旦答案有错，能立刻定位是哪份文档的问题（是文档本身错了，还是检索错了）。在企业场景，"能查证"往往比"答案漂亮"更重要。

### Q11：多轮对话是怎么管理上下文的？为什么这么设计？

**答**：策略是"最近 3 轮原文 + 更早的 LLM 摘要"。直接截断会丢早期信息（用户第一轮说的约束条件，第三轮追问时模型忘了）；全量保留又会让上下文无限膨胀，成本和延迟都失控，还会稀释关键信息。

折中方案：最新的几轮对话保留原文（细节最重要），超过阈值的历史调一次 LLM 压缩成摘要（保留话题、结论、用户偏好这类宏观信息）。这是用一次摘要调用的成本，换上下文长度恒定。

另外一个业务细节：检索时带的是**当前问题**，不是拼接历史的长文本——因为检索目标是找当前问题的资料，历史只是帮模型理解指代（"它的价格呢"里的"它"），不应该污染查询向量。

## 三、核心流程：一篇文档从上传到可检索

### Q12：完整描述文档入库的全流程

**答**：上传是异步管线，分八步：

1. **接收与注册**：API 收到文件立刻落盘，在注册表（SQLite）里登记状态 `pending`，返回任务 ID 给前端——用户不用等，前端轮询任务状态。
2. **入队**：任务进内存队列，由后台工作线程串行处理。串行是刻意设计：向量库的写入没有并发保护，多线程同时写会数据错乱。
3. **文件级去重**：算整个文件的 SHA256，和已有文档比对——内容完全一致直接标记 `duplicate` 结束，不浪费解析和向量化资源。
4. **替换更新判断**：同名但内容变了（文档改版），先删掉旧版的所有片段再入新版，避免新旧内容并存——用户会同时查到两个版本的答案，这是知识库最经典的坑。
5. **解析与切分**：按格式加载（PDF/Markdown/docx/txt），递归切分成约 500 字、带 50 字重叠的片段。重叠是为了防止关键信息正好被切在边界上。
6. **片段级去重**：每个片段再算哈希，和库里已有片段比对，重复的跳过——比如两份文档都包含同一段免责声明，只存一份。
7. **向量化与入库**：片段批量向量化写入 Chroma，刷新 BM25 索引，**同时清空查询缓存**（这步出过 bug，后面细讲）。
8. **状态落定**：全部成功标记 `available`；任何一步异常，回滚已写入的数据，标记 `failed` 并记录错误原因，方便管理员排查后重新上传。

### Q13：为什么要设计文档状态机？直接存向量库不行吗？

**答**：向量库只回答"有什么片段"，不回答"这份文档现在什么状态"。没有状态机会出现几个业务问题：

- **上传了但查不到，用户不知道为什么**——可能还在解析，可能失败了。状态机让前端能显示"解析中/可用/重复/失败"，失败还带原因，体验完全不同。
- **数据一致性没有裁决依据**——状态机（注册表）和向量库是两个存储，总会有不一致的时刻（比如进程中途挂掉）。我设计了自愈机制：以向量库的实际数据为准，定期对账，注册表里"声称可用但向量库里没有"的记录会被修正。MCP 等旁路写入的文档也能被自动纳管。
- **审计需要**——什么时间传了什么文档、处理结果如何，这是企业场景的合规底线。

### Q14：文档去重为什么做文件级和片段级两层？

**答**：两层针对不同的业务场景：

- **文件级**解决"完全重复上传"——用户重复拖同一个文件、或者两个人传了同一份制度文档。字节级一致就直接跳过，成本几乎为零。
- **片段级**解决"部分内容重复"——新文档 90% 内容和老文档一样，只更新了一章。片段级哈希让重叠部分不重复存储和向量化，只入库真正新增的部分。

另外片段哈希是持久化在向量库元数据里的，服务重启不丢；去重索引随时可以从向量库全量重建，这是"索引可重建、数据是唯一事实源"的设计原则。

### Q15：文档删除后，用户还能搜到旧内容吗？

**答**：现在不能，但这是个我踩过坑才修好的问题。

删除文档要清理**四个地方**：向量库里的片段、BM25 索引、去重索引、以及**查询缓存**。最初实现漏了缓存——删除后用户再搜，如果这个查询之前被缓存过，旧内容照样返回，而且因为缓存命中延迟极低，用户还以为系统"反应很快"，实际上是个数据幽灵。

这暴露的通用问题是：**带读缓存的系统，写路径必须枚举全部缓存点**。修复方案是入库和删除两条写路径都在成功后清空查询缓存，代价是缓存命中率在文档变更后短暂下降，换数据一致性，值得。

【深挖】清空缓存粒度会不会太粗？诚实说，当前是全量清空，对"频繁变更文档"的场景会让缓存形同虚设。细粒度方案是按文档维度做缓存键失效，但两级缓存（尤其语义缓存按查询组织）改造成本高，当前文档变更频率下全量清空是合理取舍，量级上来后再优化。

### Q16：如果文档需要紧急下架（比如涉及敏感信息），流程能保证多快生效？

**答**：删除接口是同步的——调用返回即向量库已清干净，同时清缓存和索引，所以**下一个查询就查不到了**。后台任务队列只用于"入库"这种重操作（解析向量化慢），删除是轻操作走同步路径，这正是业务语义决定的：下架必须立刻生效，上架可以慢慢来。

一个需要坦白的边界：如果有用户**正在对话中**，LLM 的上下文里已经带了旧文档的片段，这轮回答还是会基于它。彻底解决需要会话级的知识快照与撤销机制，当前版本没做，是已知的边界。

## 四、检索引擎设计决策

### Q17：RRF 融合是什么？为什么不用分数加权？

**答**：混合检索两路结果的"分数"根本不可比——向量检索输出的是余弦相似度（-1 到 1），BM25 输出的是词频统计分（无上界），直接加权平均没有意义，还得调权重，调参成本高。

RRF 的思路是不看分数只看**排名**：一个片段在两路结果里都排得靠前，融合后必然靠前。公式就是每个排名取倒数加权求和（第 1 名贡献 1/61，第 2 名 1/62……k=60 是业界通用平滑常数）。好处是无需调参、对分数分布不敏感、实现简单。代价是丢弃了分数包含的确信度信息——但在有重排兜底的情况下，召回阶段用 RRF 完全够。

### Q18：重排模型为什么只在候选集上跑，不全量跑？

**答**：CrossEncoder 的精度优势来自"问题和片段拼在一起过模型"，这也意味着它的计算量和片段数线性相关且单价高——每个候选都要一次完整的前向推理。全量片段重排，延迟会到不可用。

所以工程上固定为两阶段漏斗：召回阶段用便宜的方式（向量+BM25）把几千个片段缩到几十个，重排只处理这几十个。这是"召回求全、精排求准"的经典架构，搜索引擎也是同样的思路。

另一个实用细节：重排模型做了启动预热——第一次推理要加载模型权重，冷启动要几十秒，预热把它移到服务启动阶段，避免用户的首个请求超时。

### Q19：切分策略（500 字、50 重叠）是怎么定的？换更大或更小会怎样？

**答**：不是拍脑袋，是实验对比过 chunk_size 300 和 600 的效果定的（做了对比实验）。切分大小的业务权衡是：

- **太小**：单片段信息不完整，一个问题需要的证据分散在多个片段里，检索命中率下降；同时片段总数暴涨，检索和存储成本上升。
- **太大**：片段里混入大量无关内容，向量表示被"稀释"（一段话表达多个主题，embedding 就都不像），检索精度下降；塞给 LLM 的上下文也浪费 token。

500/50 对中文业务文档（段落语义相对集中）是个均衡点。但我会强调：**切分参数和文档类型强相关**——法律条文（条目短、编号明确）和操作手册（步骤连贯、不宜切断）的最优参数不同。理想方案是按文档类型配置切分策略，当前用统一参数是简化。

### Q20：BM25 为什么要做中文分词（jieba）？这带来什么问题？

**答**：BM25 的本质是词频匹配，英文天然有空格分词，中文没有——"知识库管理系统"不分词就是一整个 token，用户查"管理系统"就匹配不上。jieba 分词后变成"知识库/管理/系统"，子词也能命中。

带来的问题：分词质量决定 BM25 上限。专业术语容易被错误切分（产品型号、人名），这是 BM25 路线固有的维护成本，需要维护自定义词典。这也是为什么我坚持混合检索而不是纯 BM25——术语分错时还有向量检索兜底。

### Q21：embedding 用本地模型还是 API？怎么选的？

**答**：用的本地 BGE（中文优化过的开源模型），支持配置切换到 API。选本地的考虑：

1. **数据安全**：文档内容不出内网，这是企业客户的高频要求，甚至是招标硬条件。
2. **成本结构**：API 按 token 计费，入库量一大持续烧钱；本地是一次性 GPU/内存成本。检索量大的场景本地摊薄成本优势明显。
3. **确定性**：API 模型升级会导致同一文档的向量分布漂移，缓存和检索基线全部失效；本地模型版本自己控制。

代价是效果天花板略低于最强的商用 API 模型，以及要自己扛部署。我的结论：**效果敏感、数据不敏感的场景用 API；数据敏感、成本敏感的场景用本地**，所以做成了可配置。

### Q22：检索的 Top-K 是多少？上下文塞多少片段合适？

**答**：默认 Top-K 在 4~6 这个量级（可配置）。这个数字背后的权衡：K 太小，正确片段没进上下文（召回截断）；K 太大，无关片段稀释注意力，模型反而容易被带偏，token 成本也涨。有重排的情况下，排序质量高，小 K 就够；没重排才需要大 K 碰运气。

另外上下文组装是"片段+来源标注"一起给的，这让模型回答时能引用，也让"上下文里没有的问题"可以被明确拒答。

## 五、知识库治理与数据质量

### Q23：如何防止知识库"越用越乱"？

**答**：这是知识库运营的核心问题，我的方案是四道防线：

1. **入口去重**：文件级+片段级双重去重（前面讲过），从源头防止冗余。
2. **替换更新**：同名文档自动走"删旧入新"而不是并存，防止多版本打架。
3. **状态机与审计**：每份文档的来源、状态、处理记录可查，出了问题能追溯。
4. **自愈对账**：注册表和向量库定期对齐，旁路写入的孤儿数据自动纳管或清理。

坦白说还缺两块：**文档级权限**（谁能看哪份文档）和**质量准入**（入库前检查文档是不是扫描件、解析质量如何），这两块是生产化要补的。

### Q24：文档更新了，用户多久能查到新内容？

**答**：分钟级，取决于文档大小。上传即入队，解析+切分+向量化一个小文档是秒级，大文档（几百页 PDF）分钟级。生效的标志是状态变 `available`，前端可见。关键设计：**入库成功即刻清查询缓存**——否则新内容对老查询不可见（缓存返回旧结果），这是我修过的实际 bug。

### Q25：垃圾文档、过期文档怎么治理？

**答**：当前提供按来源删除的接口（前端可操作），配合文档列表的状态和元数据，管理员能定位问题文档。治理机制上还比较朴素，成熟方案应该有：文档有效期（TTL 自动下架）、使用统计（没人检索的文档归档）、血缘关系（文档替换历史），这些在规划里但没做，属于诚实的差距。

### Q26：如果用户上传的是扫描版 PDF（图片），系统能处理吗？

**答**：当前不能，会解析出空内容然后走失败状态（至少状态机会兜住，不会静默变"空文档"）。这是和真实企业落地最大的差距之一——真实企业文档里扫描件占比很高。要补的是 OCR 前置环节（解析失败时自动降级到 OCR 通道），以及表格的结构化解析。这题我会主动坦白，因为面试官若真做过企业文档系统，一定会问。

### Q27：检索不到内容时系统怎么表现？怎么防止幻觉？

**答**：三层防御：

1. **提示词约束**：明确要求"仅依据提供的资料回答，资料中没有就明确说不知道"，并给了拒答的话术模板。
2. **负样本测试**：评估集里有 5 道知识库外的问题，专门测拒答率，实测 80%，纳入 CI 门禁（阈值 0.8）。
3. **引用锚定**：要求答案带编号引用，间接强迫模型"说必有据"。

诚实说提示词约束不是硬保证，模型仍可能小概率编造。硬方案是答案生成后做忠实度校验（RAGAS 的 faithfulness 思想：逐句验证答案是否被上下文支持），在线场景可以做抽检或对高敏感场景全检。

## 六、质量保障体系：评估与门禁

### Q28：你怎么知道检索质量好不好？靠什么指标说话？

**答**：三套互补的测量体系：

**第一套：检索指标（离线实验）**——命中率（正确片段是否进 Top-K）、MRR（正确答案排多靠前）、NDCG（排序质量）、Top1 准确率。这些有标准答案，是确定性计算。结论：重排让 Top1 从 66.7% 到 100%，混合比单路向量命中率 +8.3%。

**第二套：RAGAS 生成质量（LLM-as-Judge）**——faithfulness（答案是否忠于上下文，反幻觉）、answer_relevancy（答案是否切题）、context_precision/recall（检索的片段准不准、全不全）。

**第三套：业务指标**——负样本拒答率（知识库外问题要拒答）、缓存命中率（成本效率）、延迟分布（体验）。

关键是三套各管一段：检索指标管"找得准不准"，RAGAS 管"答得好不好"，业务指标管"用户体验和成本"。

### Q29：测试集怎么设计的？怎么保证有代表性？

**答**：25 题，设计时按**问题类型分层**而不是随便凑：

1. **专有名词类**（模型名、术语缩写）——专测 BM25 价值
2. **语义改述类**（口语化问法）——专测向量检索价值
3. **跨文档易混淆类**（两份文档都有相近内容）——专测重排和排序质量
4. **负样本**（知识库外问题）——专测拒答能力

分层的目的：指标下降时能**定位是哪类能力退化了**，而不是只知道"总分掉了"。比如某次改动后专有名词类命中率掉、其他正常，立刻知道是分词或 BM25 出了问题。这个测试集是资产，每次改动都全量回归。

### Q30：LLM-as-Judge 可靠吗？怎么处理评估的不稳定性？

**答**：不可靠因素真实存在，我踩过的坑和对策：

1. **judge 输出被截断**：faithfulness 判定要求输出逐句验证的长 JSON，默认输出上限不够，被截断后解析失败——表现为指标大面积异常。对策：给 judge 显式放宽输出长度。
2. **并发限流**：评估并发一高就触发 API 限流，单题正常、批量全失败。对策：并发压到 4，加重试。
3. **nan 污染**：20 题里 1 题超时得 nan，直接求平均整列变 nan，门禁误判。对策：聚合用"忽略 nan 的均值"语义，同时统计 nan 率——**nan 率超过 30% 视为评估本身不可信，同样拦截**（评估坏了比结果坏了更危险，因为它给出的是假安心）。
4. **单次评估方差**：LLM 打分有随机性，关键结论用多次评估的稳定值，阈值留 10% 余量。

这套处理经验本身比指标数字更有面试价值——它说明我知道自动化评估的失效模式。

### Q31：评估指标怎么变成"门禁"的？流程是什么？

**答**：流水线是：push/PR 触发 CI → 跑 lint → 跑评估脚本（25 题全量过 RAG 管线 → RAGAS 计算五指标）→ 任何指标低于阈值就 exit 1，CI 红灯拦截合并 → 报告落盘（JSON 明细 + Markdown 摘要，含逐题得分）。

阈值校准有讲究：**先跑基线，再定阈值**，取基线值留 10% 余量，而不是拍一个"看起来不错"的数。阈值支持环境变量覆盖，不同环境可以松紧不同。另外 CI 在没有配 API Key 的环境（比如 fork PR）会优雅跳过评估而不是失败——门禁不能把协作流程卡死。

### Q32：如果门禁拦住了你的合并，但你觉得是误报，怎么办？

**答**：分三步：先看报告明细定位是哪类题、哪个指标掉了；再判断是**真退化**（代码问题，必须修）、**评估波动**（LLM judge 随机性，重跑确认）还是**阈值不合理**（基线漂移，需要重新校准）。有 --no-gate 参数可以只跑评估不拦截，用于排查。原则上不能随手跳过门禁——门禁的公信力一旦被"特殊情况下绕过"破坏，就名存实亡了。真要放行，走调阈值的明流程，留下记录。

### Q33：评估体系现在最大的局限是什么？

**答**：三个诚实的问题：

1. **测试集只有 25 题**，覆盖不了真实用户查询的长尾分布；生产化应该从真实查询日志里持续采样扩充测试集（还要去隐私）。
2. **LLM judge 本身有偏差**：judge 倾向给长答案打高分、容易被表面流畅度迷惑。缓解办法是多 judge 投票或人工抽检校准，当前用的单 judge。
3. **离线评估 ≠ 在线体验**：用户满意度、任务完成率这些在线指标（A/B、用户反馈闭环）才是终极标准，当前全部是离线体系。

## 七、架构与工程化

### Q34：为什么选 FastAPI？同步的 RAG 引擎怎么配合异步框架？

**答**：选 FastAPI 因为它原生异步、自动生成 API 文档（Swagger）、Pydantic 数据校验内建、生态成熟，Python 技术栈里做 AI 服务的事实标准。

核心问题是：**检索引擎（embedding 推理、向量库、重排模型）全是同步阻塞的**，直接在异步框架里调用会卡死事件循环——一个慢查询会拖住所有请求。解法是分层处理：

- **阻塞操作线程池化**：推理类调用扔进线程池执行，事件循环继续处理别的请求，并发能力恢复。
- **LLM 调用真异步**：换异步客户端，流式输出逐 token 推给前端，首字延迟大幅下降。
- **重操作异步化到后台**：文档入库不占用请求线程，任务队列异步消化，接口秒回。

### Q35：为什么用后台任务队列而不是 Celery 这种成熟方案？

**答**：刻意的克制。当前是单进程部署、单工作者线程串行处理，原因有三：

1. **下游不支持并发写**：向量库的写入没有并发保护，多个 worker 同时写会数据错乱——先解决正确性，再谈吞吐。
2. **避免过度设计**：文档入库的量级（每天几十上百份）根本用不着分布式队列，引入 Celery 要多维护 broker、worker、监控三套东西。
3. **接口语义已对齐**：提交任务/查询任务状态的接口抽象好了，量级上来换 Celery 后端时，上层代码不动。

这是我认可的工程判断：**架构演进跟着真实量级走，接口先抽象好，实现后置**。

### Q36：为什么用 SQLite 而不是 MySQL/PostgreSQL？

**答**：当前阶段 SQLite 是对的：零运维、单文件、备份就是复制文件、性能对当前量级绰绰有余。用它存了两类数据：文档注册表（状态机）和用户/Key 数据。

但这是有意识的过渡选型，边界很清楚：SQLite 的写并发锁是库级的，多进程部署、写密集场景就是瓶颈。数据访问层做了薄封装，迁移 PostgreSQL 时换连接和 DDL 即可，业务代码不动。**选型的成熟度体现在知道什么时候该换，而不是一开始就上最重的**。

### Q37：为什么用 Chroma？什么时候换 Milvus/pgvector？

**答**：Chroma 的定位是嵌入式向量库——进程内启动、零部署，适合当前单机量级（万级片段）和快速迭代。换库的触发条件明确：

- **数据量**：百万级以上片段，Chroma 的索引和查询性能撑不住
- **高可用**：Chroma 是单机无副本，业务要求服务不中断就要换
- **多租户隔离**：按租户分 collection 的强隔离需求，Milvus 的多 collection 管理更成熟

候选里 pgvector 的优势是"如果已经有 PostgreSQL，向量只是一张表"，运维体系复用；Milvus 优势是专门的分布式向量能力。当前引擎层做了向量库的接口封装，替换成本被刻意压低了。

### Q38：会话状态存哪？用户刷新页面对话还在吗？

**答**：诚实回答：当前对话历史在前端（内存+本地存储），刷新不丢（本地存储还在），但**换设备/清缓存就没了**。后端对话接口是无状态设计——历史由前端传入，服务端不存会话。

这是有意的简化：无状态服务水平扩展最简单。生产化补齐方案：会话落库（SQLite/PG 存对话记录），前端只持有会话 ID。改造点已隔离在接口层，不难。这又是一个"知道差距在哪"的例子。

## 八、安全设计

### Q39：鉴权为什么设计成 JWT 和 API Key 两个通道？

**答**：两类消费者特性完全不同：

- **JWT 给人用**（Web 前端）：有登录交互，token 有过期时间（12 小时），适合会话型访问。
- **API Key 给系统用**（服务集成、脚本）：没有交互流程，Key 长期有效但要能随时吊销——密钥泄露时一秒切断，还要有"最后使用时间"来发现僵尸 Key。

细节设计上：密码存储用 PBKDF2 加随机盐慢哈希（数据库泄露也还原不出明文）；API Key 明文只在创建时展示一次，库里只存哈希和前缀（列表里能认出来但不能还原）；首个注册用户自动成为 admin（Bootstrap 机制，避免初始权限的鸡生蛋问题）。

### Q40：如果 JWT 密钥没配置，系统怎么表现？

**答**：这是我有意设计的**安全降级**：没配置密钥时每次启动随机生成一个，效果是重启后所有已发 token 失效——用户要重新登录，但系统不会因为没配密钥而拒绝启动（开发体验），也不会用弱密钥长期运行（安全底线）。启动日志有明确告警。生产部署必配固定密钥，这是部署 checklist 的一条。

这个设计背后的原则：**安全配置缺失时，选择"安全地不可用"或"安全地降级"，绝不能"不安全地可用"**。

### Q41：文档内容里有敏感信息，系统怎么防泄露？

**答**：分层来说：

- **传输/存储层**：本地模型路线（embedding 不出网）、数据都在自有存储。
- **访问层**：鉴权挡住了未授权访问；但**当前没有文档级权限**——所有登录用户能查所有文档，这是和真实企业需求的最大差距。生产方案是文档带权限标签，检索时按用户可见范围过滤（向量检索后过滤或检索前按 collection 隔离）。
- **生成层**：引用标注让"答案依据什么"透明，间接帮助审计。

这块我会主动讲差距，因为多租户/权限是 RAG 落地企业最常被问的硬问题，回避反而显得没想过。

### Q42：API 限流做了吗？没做的话怎么规划？

**答**：没做，诚实承认。当前是内部系统量级，鉴权之后没有限流。规划是明确的：接入层按用户/Key 维度限流（比如 slowapi 或网关层），LLM 调用按 token 配额单独限制（因为 LLM 成本大头在生成，一个超长上下文请求比一百个检索请求还贵）。优先级上排在多租户之后，因为限流保护的是"我自己不被打挂"，而权限保护的是"用户数据不被越权"，后者风险更高。

## 九、可观测性与运维

### Q43：可观测性做了什么？为什么它重要？

**答**：三件事：

1. **结构化日志**：所有关键事件（检索完成、生成完成、入库完成、HTTP 请求）都是带字段的结构化数据（JSON 格式），而不是自由文本。开发环境彩色控制台，生产一行一条 JSON 给日志平台直接采集。查问题时按字段过滤（"所有缓存命中的请求延迟"）秒级完成。
2. **请求 ID 全链路贯穿**：每个请求生成唯一 ID，这个请求触发的每条日志都带它。用户反馈"刚才那个回答不对"，拿 ID 一查，完整还原当时的检索结果、延迟、命中情况——**没有这个，线上问题基本靠猜**。
3. **Langfuse 追踪**：记录每次检索和生成的 trace 层级（延迟、token 消耗、检索来源），用于成本分析和质量回溯。关键设计是**未配置时零开销降级**——可观测性组件不能成为系统的可用性依赖。

业务价值一句话：**线上系统没有可观测性，等于闭着眼睛开车**。RAG 系统尤其需要，因为它的失败是"静默劣化"（检索质量慢慢变差）而不是崩溃，没有指标根本发现不了。

### Q44：日志里你最关心哪些指标？为什么？

**答**：按故障排查价值排序：

- **缓存命中率**：异常下降说明文档变更频繁或缓存策略有问题，直接影响成本。
- **检索延迟分布**（P50/P95）：P95 恶化说明量级上来或索引没重建。
- **拒答率**：突然升高说明知识库覆盖出问题了（文档被误删、检索退化）。
- **token 消耗**：成本监控，异常飙升可能是上下文组装出了问题。
- **入库失败率**：数据管线健康度。

这些都有对应的结构化日志事件，可以直接接入监控告警。

### Q45：如果用户反馈"回答不准"，你的排查路径是什么？

**答**：固定四步，不瞎猜：

1. **拿请求 ID 还原现场**：日志里看当时的检索结果——是检索错了（召回的片段就不对）还是生成错了（片段对但答案跑偏）。
2. **检索错 → 看四阶段详情**：向量/BM25 各自召回什么、RRF 融合后排序、重排有没有救回来。哪一阶段开始错的，指向不同的问题（切分？embedding 质量？分词？）。
3. **生成错 → 看上下文和提示词**：片段是对的但模型没用好（上下文太长稀释、指令不够强），还是模型能力问题。
4. **同类问题回归**：把这个 case 加进测试集，修复后回归验证——**用户的每个 bad case 都是测试集的增量资产**。

这个排查路径本身就把"四阶段检索可视化"的价值讲清楚了：它是调试工具，不只是炫技界面。

### Q46：系统挂了怎么恢复？数据会丢吗？

**答**：分层数据、分层恢复：

- **向量库、注册表、用户库**都是本地持久化存储，进程重启数据都在。
- **内存中的任务队列**会丢（正在处理但没完成的文档），但状态机里它们停在 `parsing`，对账机制会发现"解析中超时"的记录并标记失败，用户重新上传即可。状态机让崩溃恢复有据可依。
- **缓存**丢了就丢了——它本来就是可再生数据，冷启动后重新预热。

诚实差距：没有做多副本和高可用，单机故障就是服务中断。当前定位是单机可恢复，不是高可用。

## 十、生产落地差距与扩展规划

### Q47：这个系统离真实生产还差什么？（诚实版）

**答**：我主动梳理过，按风险排序：

1. **文档解析深度**：扫描件 OCR、表格结构化、图片理解——真实企业文档这三类占比很高，当前解析是朴素文本抽取。
2. **多租户与文档级权限**：当前所有用户共享全量知识库，SaaS 化必须按租户隔离（数据层分 collection 或加权限过滤）。
3. **高可用**：单进程单机，无副本；向量库 Chroma 不支持分布式。
4. **会话持久化**：对话历史在前端，没有服务端会话管理。
5. **限流与配额**：没做，恶意/失控调用会打挂服务。
6. **在线反馈闭环**：用户点赞点踩回流到测试集和模型调优，当前只有离线评估。

我的优先级判断：权限 > 解析深度 > 高可用，因为数据越权是安全事故，其他是体验问题。

### Q48：如果文档量从现在的几十份涨到十万份，架构要动哪里？

**答**：逐层评估：

- **向量库**：Chroma 到百万级片段性能衰减，迁移 Milvus（分布式、专门为这个量级设计），引擎层接口已封装，替换成本可控。
- **检索链路**：BM25 索引要重建机制升级（增量更新而不是全量），重排候选量可能要分层（粗排→精排两级）。
- **入库管线**：单线程串行吞吐不够，上分布式任务队列（Celery + 多 worker），前提是先解决向量库的并发写。
- **缓存**：语义缓存的 FAISS 索引本身要考虑分片。
- **存储**：SQLite 注册表换 PostgreSQL（写并发）。

关键回答点：**每层的扩展触发条件我都清楚，且接口抽象为替换预留了缝**——这就是"设计时想过量级"和"够用就行"的区别。

### Q49：如果并发用户从 1 涨到 1000，瓶颈在哪？

**答**：按请求链路推演瓶颈顺序：

1. **LLM 生成是第一瓶颈**——每个请求几秒的模型调用，1000 并发直接打爆 API 配额/自建 GPU。解法：流式（体验缓解）、并发池管控、请求排队、更小的模型做简单问题（路由分级）。
2. **embedding 推理**——CPU 推理是百毫秒级，高并发下排队；上 GPU 或推理服务化（Triton）。
3. **重排模型**——同样 GPU 资源竞争，可能要批处理化（攒批推理提吞吐）。
4. **最后才是 API 层**——FastAPI 异步架构本身撑得住，线程池大小和连接池调优即可。

有意思的结论：**RAG 系统的扩展压力几乎全在模型推理，不在 Web 层**——这决定了扩容预算应该花在 GPU 而不是加 API 服务器。

### Q50：成本上你怎么优化的？

**答**：四个已落地的手段，按收益排：

1. **两级查询缓存**：高频问题命中后跳过全链路（检索+重排+生成全免），重复问题的边际成本趋近于零。语义缓存让"换个问法"也能命中，命中率比纯精确缓存高一截。
2. **本地 embedding**：向量化不按 token 付费，入库成本从持续支出变一次性投入。
3. **上下文控制**：Top-K 限制 + 历史摘要压缩，token 消耗直接受控。
4. **重排只处理小候选集**：GPU 推理量控制在最小必要范围。

规划中：小模型路由（简单问题用便宜模型）、token 用量按用户/Key 统计做配额。

### Q51：如果让你重新做一遍，你会改什么？

**答**：三个真实的反思：

1. **数据层选型再前置一步**：一开始就用 PostgreSQL（带 pgvector），省掉"SQLite 到处用、后来要迁"的心理负担——量级不确定时，通用数据库比专用组件的决策成本低。
2. **测试集先行**：应该在写检索引擎之前就建测试集——先有尺子再做东西，每次迭代的回归成本会低很多。实际是先做了引擎后补的评估，中间一段"盲改"期。
3. **权限模型设计再早一点**：现在补多租户要动的层比较多（存储、检索、缓存都要带租户上下文），一开始就留字段的话是顺路的事。这教训 generalize 成一句话：**和安全、多租户相关的设计，永远在第一天就占位，哪怕不实现**。

## 十一、深挖故事：困难问题的解决

> 面试官最爱的一类问题："讲一个你解决过的最难的问题"。以下五个故事都真实发生过，按讲述价值排序。

### Q52：讲一个你印象最深的 bug

**答**（缓存幽灵事件）：

**现象**：全量回归测试发现——删除文档后，用户再搜同样的关键词，**已删除的内容还在返回**。更诡异的是延迟极低，看起来"系统反应很快"，实际是数据幽灵。

**排查**：先确认删除本身是成功的（向量库里确实没了）——那内容从哪来的？顺着请求链路找，发现是**查询缓存**：删除前有人搜过这个词，结果进了缓存；删除操作清理了向量库、BM25 索引、去重索引三个地方，唯独漏了缓存。缓存命中直接返回旧结果，根本没走到向量库。

**修复与反思**：入库和删除两条写路径都补上"成功后清空查询缓存"。这个 bug 教会我两件事：一是**带读缓存的系统，写路径要做"失效清单"**——改数据时把所有缓存点列出来逐项核对，我们的清单是：向量库、BM25、去重索引、注册表、查询缓存五处；二是**这类 bug 单元测试发现不了**（要构造"写后读同一查询"的时序），必须是端到端回归测试覆盖写后读路径。后来我把这个场景固化进了回归测试。

### Q53：讲一个"看起来是代码问题、实际是环境问题"的排查

**答**（幽灵进程事件）：

新写的鉴权接口测试全部 404，代码反复检查没有任何问题。惯性思路是继续盯代码，但转念一想：**验证响应到底是不是我的服务发出的**。拉取接口文档（openapi.json）对比——里面竟然有不属于这个项目的路由！说明 8000 端口上响应请求的是**别的进程**。查端口占用，发现是之前某次测试的 uvicorn 进程没杀干净，它监听 0.0.0.0，我的新服务监听 127.0.0.1，两者共存，请求被分流到旧进程。强杀残留进程后一切正常。

方法论总结：**"代码正确但行为诡异"时，先怀疑环境再怀疑代码**；用"事实采集"（接口文档、端口占用、进程列表）代替"代码阅读"——让系统自己告诉你状态。排查顺序固化为：环境 → 数据 → 代码。

### Q54：讲一个第三方库/依赖的坑

**答**（评估框架的版本断层）：

引入 RAGAS 评估框架时，按记忆里的 API 写代码，连续报"模块不存在"、"方法不存在"。冷静下来意识到：**这种快速迭代的 AI 库，文档和记忆都可能是过时的**（RAGAS 从 0.2 到 0.4 经历大重构，接口全变了）。

改变策略：不再猜，先在解释器里枚举真实 API——看模块到底导出什么、函数签名长什么样，逐个验证后再写代码。之后又连续解决了三个衍生问题：内置 embedding 封装缺接口（自己写适配器桥接到项目的本地模型，反而更好——模型复用、零 API 成本）；judge 模型输出被默认长度上限截断导致解析失败（显式放宽输出上限）；评估并发触发 API 限流、指标全空（降并发加重试）。

这系列问题的元教训：**AI 生态的库，"记忆"是负资产，验证是唯一可信来源**。识别信号也总结出来了：模块不存在/属性不存在/参数不匹配三类报错连着来，基本就是版本错位，停止微调代码，先验证 API。

### Q55：讲一个数值/数据处理的坑

**答**（nan 污染事件）：

评估 20 题里 19 题分数正常，1 题超时得了 nan（LLM judge 没返回有效分）。按理说均值应该忽略这一题，结果整列均值直接显示 nan——因为 Python 里 nan 有传染性：任何数加 nan 都变 nan，一行朴素的求和取平均把整个指标毁了。更严重的是门禁跟着误判（nan 不大于阈值，全列 FAIL）。

修复三层：聚合时显式过滤 nan；统计 nan 数量进报告；门禁加规则——**nan 率超过 30% 视为"评估本身不可信"同样拦截**。最后一层是关键认知：评估系统坏了比被评估对象坏了更危险，因为它制造**假的安心或假的警报**。后来又在报告序列化时发现 nan 会输出非法 JSON（NaN 字面量），一并做了清理。

教训 generalize：**任何涉及 LLM 打分的聚合计算，必须用"忽略 nan 的均值"语义，且把 nan 率当一级公民监控**。

### Q56：讲一个设计权衡的决策过程

**答**（要不要上 Celery 的决策）：

做数据管线时，"企业级"的直觉说该用 Celery（成熟、分布式、面试也好听）。但分析实际约束：向量库写入没有并发保护（多 worker 会写坏数据）、文档量级一天几十份（单线程绰绰有余）、单进程部署（分布式队列没有意义）——三条都指向**不该上**。

最终方案：进程内任务队列 + 单 worker 串行，但**接口抽象按任务队列语义设计**（提交任务、查询状态、异步返回任务 ID）。这样量级真上来时，换 Celery 后端上层代码零改动。

这个决策的元原则：**架构复杂度要匹配真实量级而不是想象中的量级；但接口抽象要预留给演进留缝**。过度设计不是"更专业"，是把未来的维护成本提前支付，而且大概率白付。

## 十二、开放性问题与场景应对

### Q57：如果老板说"效果不好，准确率太低"，你怎么办？

**答**：先定义再优化，不直接调参数。第一步是把"不好"翻译成可测量的东西：是**检索不到**（正确片段没进上下文）、**检索到了但答案错**（生成问题）、还是**答非所问**（理解问题）？拿具体 bad case 走排查路径（见 Q45）归类。

然后按类施策：检索类问题优先调（切分参数、混合权重、召回量——这些是低成本高收益旋钮）；生成类问题调提示词和上下文组装；理解类问题考虑查询改写（把口语问题先改写成规范检索式）。

同时**把每个 bad case 沉淀进测试集**，改动后回归对比——"准确率太低"这种主观感受，最终要变成"命中率从 X 到 Y"的客观曲线，这也是和老板沟通的语言。

### Q58：如果用户要求"回答必须 100% 准确"，你怎么回应？

**答**：技术诚实 + 方案分层。直接说：LLM 生成环节做不到数学意义的 100%，但可以工程化逼近——

1. **强拒答策略**：上下文无充分证据时宁可说"不知道"，把幻觉率压到最低（负样本拒答率进 CI 门禁）。
2. **引用锚定**：每个结论带文档出处，准确性的责任部分转移为"文档本身是否准确"。
3. **高敏场景旁路**：真正 100% 要求的场景（合规话术、法律条款）不该走生成——直接检索返回原文片段，零幻觉，牺牲的只是"顺口"。
4. **人审闭环**：高风险回答进人工审核队列，审过的进缓存复用。

关键是把"100% 准确"的需求拆成"哪些环节可以确定性保证（检索、拒答、原文返回），哪些只能概率保证（生成）"，和业务方对齐预期。

### Q59：知识库需要每天同步几万份新文档（比如新闻/研报），当前架构扛得住吗？

**答**：扛不住，明确说要动三处：

1. **入库吞吐**：单 worker 串行是每分钟几份的量级，要上分布式队列 + 多 worker，**前置条件**是向量库换支持并发写的（Milvus）。
2. **索引实时性**：BM25 全量重建扛不住高频变更，要增量索引；缓存频繁失效会让命中率崩掉，缓存策略要按文档变更频率分级（热数据变更低、冷数据缓存久）。
3. **知识时效语义**：这是业务层新问题——旧文档自动降权或过期（TTL），检索结果倾向新内容，否则"上周的研报结论"和"今天的"混在一起，答案自相矛盾。

这个问题的价值在于暴露"实时性"不只是吞吐问题，还有**知识版本语义**问题——后者经常被忽略。

### Q60：如果要支持多部门各自独立的知识库（互不可见），怎么改？

**答**：多租户改造，从数据到检索全链路带租户上下文：

1. **存储隔离**：每租户独立 collection（强隔离、简单粗暴、租户多时管理重）或共享 collection 加租户字段过滤（省资源、过滤要可靠）。我的倾向：租户数少（部门级）用独立 collection，租户数大（SaaS 级）用字段过滤。
2. **检索链路**：所有查询带租户标识，向量检索和 BM25 都要按租户过滤——**语义缓存的 key 也要带租户**，否则 A 部门的问题命中 B 部门的缓存，就是数据越权事故。
3. **鉴权层**：JWT 里带租户和角色，API Key 绑定租户。
4. **文档管线**：入库时打租户标签，删除、统计、配额全部按租户维度。

改造难点恰恰在容易被忽略的缓存层——这是我在回答里主动展示"想得全"的机会。

### Q61：如果让你给这个项目排下一季度的迭代，怎么排？

**答**：按"风险消除 > 价值提升 > 体验优化"排：

1. **多租户与文档权限**（风险消除）：数据越权是安全事故级别，最高优先。
2. **文档解析增强**（价值提升）：OCR + 表格解析，直接扩大可接入的文档范围，业务价值立竿见影。
3. **在线反馈闭环**（价值提升）：用户点赞点踩回流测试集，评估体系从离线走向在线，形成数据飞轮。
4. **会话持久化 + 历史管理**（体验优化）：服务端会话，跨设备漫游。
5. **容器化部署 + 高可用**（体验优化）：Docker Compose 编排，为上量做准备。

这个排序的逻辑：前两项解决"能不能给企业用"，后三项解决"用得好不好"——先过可用门槛，再谈体验。

### Q62：你在这个项目里最大的成长是什么？

**答**：（结合个人情况润色，供参考）三个层面的转变：

1. **从"实现功能"到"经营质量"**：以前写代码的目标是"能跑"，这个项目让我建立了完整的质量观——测试集是尺子、评估是测量、CI 门禁是护栏，改动不再靠感觉而是靠回归数据。
2. **从"技术正确"到"系统正确"**：缓存一致性那个 bug 教育了我——每个组件单独都对，组合起来照样错。写路径要枚举所有缓存点、双存储要对账、评估系统自己也要被监控，**正确性是系统属性，不是组件属性**。
3. **对工程判断力的敬畏**：什么时候该克制（不上 Celery）、什么时候该前置（权限模型第一天占位）、阈值怎么定（先基线后阈值）——这些没有标准答案的决策，才是工程和 coding 的区别。
